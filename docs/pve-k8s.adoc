= Kubernetes Clusters on Proxmox VE
:toc: left
:sectnums:

Administrator and user guide for the `pve-k8s-manager`
package. Everything described here is implemented and
covered by the unit suite (`tests/unit/`); end-to-end
behaviour is validated in a nested Proxmox lab
(acceptance scenarios S1-S6, `tests/lab-acceptance.sh`,
last full run 2026-11-02). Physical-hardware validation
(T4.2) is still pending - see <<limitations>>.

== Concepts

* Clusters run on *VMs only* (no LXC, no kubeadm on the
  PVE hosts). Node VMs are built from immutable, versioned
  Debian templates and are *never patched in place*:
  rolling changes and Kubernetes upgrades replace nodes
  one at a time (surge, at most one extra node,
  `maxSurge=1` semantics).
* The user manages only Kubernetes-level concerns -
  version, node groups, add-ons. Nobody SSHes into a node
  to run `apt upgrade`; a node with a problem is replaced.
* Control planes are 1, 3 or 5 VMs with stacked etcd and
  a kube-vip virtual IP.
* Workers live in *node groups* (pools) with per-group
  size, scaler bounds, labels, taints, host placement,
  storage and CPU architecture.
* Cilium is the only CNI. Networking fits Proxmox SDN:
  clusters share an EVPN zone (tenant VRF) and each
  cluster gets its own VNet.
* Autoscaling runs *outside* Kubernetes, on the PVE
  hosts, leader-elected. It simulates pods against whole
  VMs; there is no in-cluster autoscaler to babysit.
* Written upstream-first: Perl API2 endpoints and
  orchestration, ExtJS UI, AGPL. The integration points
  into stock pve-manager files are listed in
  `INTEGRATION.md`.

== Cluster lifecycle

=== Create

UI: Datacenter -> Kubernetes -> Create. The form asks
only for a name, the Kubernetes version (dropdown),
the control-plane size (1/3/5), a storage (selector over
existing PVE storages) and an SDN zone (selector over
existing zones). Advanced fields (collapsed) cover the
public/node subnets, gateway, LB range, template builder
IP and control-plane architecture.

API:

[source,sh]
----
pvesh create /cluster/k8s --name c1 --k8s-version 1.36 \
    --cp 3 --sdn-zone evpnzone \
    --public-subnet 192.168.205.0/24 \
    --node-subnet 192.168.206.0/24 \
    --storage local-lvm --builder-ip 192.168.206.50
----

Creating records the cluster (`state: config-only`);
nothing is built until provision. Kubernetes 1.35, 1.36
and 1.37 can be created; 1.36 is the default. 1.37 is a
*preview*: only Cilium 1.21 is tested with it, and 1.21
is still a pre-release, so 1.37 clusters get that
pre-release (1.21.0-pre.4). Once Cilium 1.21.0 is
released, the pin moves to it and the preview label goes
away. Upgrading to a minor that needs a newer Cilium
upgrades Cilium first, one Cilium minor at a time; the
upgrade check shows that step and refuses a jump of two
Cilium minors.

Each minor shows its upstream support window: the
create dialog shows the end-of-life date, and the
cluster Overview shows the running minor's status.
That status is a warning once the minor is in upstream
maintenance (critical fixes only, the last two months)
and critical after its end of life. A minor past its end
of life is refused for new clusters unless `--allow-eol 1`
is passed. The upgrade check warns when the target is
already in maintenance. The dates are recorded in
`PVE::K8s::Config` (from kubernetes.io/releases) and
updated with each release.

=== Provision

`pvesh create /cluster/k8s/c1/provision` (or the
Provision button) converges the cluster to its record:
networks, templates, VMs, kubeadm bootstrap, add-ons.
It is resumable and idempotent - rerunning it after an
interruption adopts live nodes instead of duplicating
them, and an orphaned in-flight node is adopted, never
double-created (proven by a kill-resume acceptance gate:
worker killed with `kill -9` mid-surge, resume completed
with exactly the declared membership).

If no template exists for the requested version and a
builder IP was recorded at create time, the plugin
builds its own template on a builder VM; a fresh install
needs no manual template work. Templates are named
`k8s-node-<minor>-r<revision>` (`-arm64` suffixed on
ARM64) and distributed to the hosts that need them:
copied per host for node-local storage, one central copy
for shared storage.

Provision also *converges node-group membership*: nodes
beyond a group's declared size are drained and retired
(highest index first), missing nodes are created. This
is the pass that makes group edits take effect.

=== One action at a time

Mutating actions (provision, roll, upgrade, scale, power,
node drain/replace/force-retire, volume move, backup,
restore, evacuate, add-on enable/disable, delete, and
settings edits) are serialized per cluster by a claim
recorded in the cluster record and visible on every PVE
host. Starting the *same* action again while it runs -
for example clicking Provision twice because it is slow -
does not fork a second worker: the request returns the
running task's UPID, so the UI simply shows that task.
Starting a *different* action, or editing settings, while
one runs is refused with an error naming the running
action; wait for it to finish. Actions are never queued
with stale parameters. The claim is heartbeated by its
worker; if a worker is killed, the claim goes stale after
30 minutes and the action can be started again (provision
then resumes and adopts live nodes). The Overview panel
shows the running action while one is live. The scaler
and backup timers stand down quietly while a user action
holds the cluster.

=== Roll

`pvesh create /cluster/k8s/c1/roll` replaces every node,
one at a time with one surge node, onto the current
template revision - this is how OS and kubelet changes
reach nodes. Rolls honour the cluster's maintenance
window (`maintenance-window`, HH:MM-HH:MM) unless forced
(`--force 1`). CP members are only ever rolled onto
images whose revision the plugin has recorded as tested
for the control plane.

=== Upgrade

`pvesh create /cluster/k8s/c1/upgrade --to 1.36`
upgrades one minor at a time (1.35 -> 1.36 is the tested
path): kubeadm upgrade on the control plane, then node
replacement. The plugin records the applied version
(`upgrade-applied`) so a resume never re-applies a
half-finished upgrade or accumulates surge control
planes.

=== Power

`pvesh create /cluster/k8s/c1/power --action start|stop`
boots or stops all node VMs as one operation: start is
control-plane first, stop is workers first. (Used in the
lab to recover whole clusters after host restarts.)

=== Delete

`pvesh delete /cluster/k8s/c1` (Destroy in the UI)
removes the cluster with an orphan audit: node VMs and
their disks, the cluster VNet, plugin users/tokens and
snippets are all removed; the acceptance suite verifies
zero leftovers (`qm list`, resource list and VNet list
all clean).

=== Kubeconfig

`pvesh get /cluster/k8s/c1/kubeconfig [--hours N]`
(Overview -> Kubeconfig in the UI) issues a kubeconfig
for the calling PVE user or API token:

* *Identity*: a service account of its own in
  `pve-k8s-users`, so the Kubernetes audit log names
  who acted. pve-k8s itself uses a separate account
  (`kube-system/pve-k8s-manager`).
* *Role* from the PVE privilege on `/cluster`:
  `Sys.Modify` gets `cluster-admin`; `Sys.Audit` gets
  read-only access (`view`, plus nodes, namespaces and
  storage; no secrets).
* *Validity*: a TokenRequest token, 1 hour by default,
  up to the cluster's `kubeconfig-max-hours` (Settings;
  default 24, at most 720). Nothing static, nothing
  that never expires.
* *Revoke*: the Access page (`GET .../access`) lists who
  was issued one; `DELETE .../access/{userid}`
  (`Sys.Modify`) deletes that account, so every token
  issued to it stops working at once.

==== Auto-refresh

For daily use, choose *Auto-refresh* as the validity
(`pvesh create /cluster/k8s/c1/kubeconfig --url
https://pve.example.com:8006`). Instead of a Kubernetes
token, the kubeconfig carries a PVE API token,
`<user>!k8s-<cluster>`, which pve-k8s creates under the
calling user. The token is privilege separated and has
no permissions of its own, so it cannot do anything else
in the PVE API and a leaked kubeconfig is not a PVE
login. When it asks for credentials, its user's
privileges decide the role, so the role keeps following
them. Tokens made by earlier versions (without privilege
separation) are narrowed by the scaler timer; their
secret, and so their kubeconfig, stays valid. kubectl runs `pve-k8s-auth` (an exec
credential plugin, like `aws eks get-token`), which
trades the API token for a 1-hour Kubernetes token
(`GET .../credential`) and caches it until 5 minutes
before it expires.

* `pve-k8s-auth` is one Python 3 file with no
  dependencies. Download it from the Kubeconfig window
  (it is also installed as `/usr/sbin/pve-k8s-auth` on
  every PVE host) and put it on your `PATH`.
* The PVE certificate is checked against the PVE
  cluster CA, which the kubeconfig carries, or against a
  CA the system trusts.
* There is one such token per user and cluster. Issuing
  a new auto-refresh kubeconfig gives it a new secret and
  a new identity, so the previous kubeconfig stops at
  once.
* Revoking a user also deletes its `k8s-<cluster>` API
  token. So does deleting the token under Permissions ->
  API Tokens; either way kubectl gets no new token after
  that. Revoke stops the current token at once as well.
* A login that is itself an API token cannot create
  one; give that token to `pve-k8s-auth` directly
  (environment variable `PVE_K8S_API_TOKEN`).

Tokens are issued over the control plane's vsock
channel, typically in well under a second; guest exec
is the fallback. pve-k8s's own token renews itself the
same way before it expires.

The cluster's own admin certificate stays on the
control-plane VMs and is never handed out.

== Node groups

A group is a JSON object in the cluster's `pools`:

[source,json]
----
[{ "name": "default", "size": 2, "min": 1, "max": 3,
   "labels": "tier=web", "taints": "",
   "hosts": "pve1,pve2", "storage": "local-lvm",
   "arch": "amd64" }]
----

* `size` - declared node count. Provision converges to
  it (adds missing, drains and retires excess).
* `min` / `max` - bounds for the pod-driven scaler
  (below). The scaler moves `size` only inside
  [`min`, `max`] and only in reaction to pods.
* `labels` / `taints` - applied to the group's nodes
  (also used by scaler simulation).
* `hosts` - optional placement: only these PVE hosts
  receive the group's nodes.
* `storage` - optional per-group disk storage override.
* `arch` - `amd64` or `arm64`; see <<multiarch>>.

UI: cluster page -> Nodes -> Node Groups (Create / Edit
/ Delete). Saving stores the groups and immediately
converges membership via a provision pass. Deleting a
group drains and retires its nodes. The control plane
is not a group: its count is fixed at creation.

Groups can also be managed over the API:
`PUT /cluster/k8s/{name}` with a `pools` JSON string
(validated eagerly; a bad group is rejected before
anything is stored).

== Control plane

* 1, 3 or 5 members, stacked etcd, kube-vip VIP on the
  public subnet. kube-vip runs as a static pod on every
  CP; the VIP is the API endpoint in every kubeconfig.
* Placement spreads CPs across PVE hosts (and HA
  groups where present) on a best-effort basis.
  *Hard* anti-affinity (never two CPs on one host while
  enough hosts are eligible) is follow-up P2 - today a
  small host count can still co-locate CPs.
* Certificates: `GET /cluster/k8s/{name}/certificates`
  reports expiry of every kubeadm PKI certificate
  (`admin.conf`, `apiserver`, etcd, ... days remaining
  and a level of ok/warning/critical). The one-year
  kubeadm PKI is renewed by rolling or upgrading the
  control plane; the Overview shows the worst level.

=== How pve-k8s reaches the API

The PVE hosts have no IP route into a cluster's node
subnet. pve-k8s talks to Kubernetes over two channels:

* *vsock* (the default for API calls). Every
  control-plane VM has a virtio-vsock device, and a
  small proxy in the guest forwards it to the local API
  server. Reads, cordon/uncordon, labels, node deletes,
  PV/PVC changes and re-creation (volume moves), events,
  pod metrics and token issuing go this way,
  as HTTPS with pve-k8s's own service-account token, in
  well under a second per call.
* *Guest agent exec* (`qm guest exec`, a few seconds
  per call). It is used for work inside the VM
  (`kubeadm`, packages, files, etcd snapshots), for the
  commands that stay with kubectl (`drain`, `taint`,
  add-on manifests), and as the fallback when vsock does not
  answer: older nodes, the proxy down, or the API
  server not up yet. After a failure, vsock is skipped
  for two minutes for that VM, or for the whole cluster
  when pve-k8s has no token for it yet, so the
  fallback costs one try.

== Networking

* One EVPN SDN zone acts as the tenant VRF for all
  clusters. Each cluster gets a dedicated VNet
  (`k8s` + 5 characters - PVE caps VNet ids at 8) in
  that zone, an internal *node subnet* (node IPs, etcd,
  kubelet) and a *public subnet* carrying the
  control-plane VIP and LoadBalancer IPs. Creating or
  deleting a cluster needs no router or fabric
  reconfiguration.
* Cilium is the CNI (eBPF, kube-proxy replacement) and
  provides the ingress controller and Gateway API by
  default. pve-k8s installs the Gateway API CRDs itself
  (v1.6.3, experimental channel, applied server-side)
  before Cilium, at the version Cilium documents.
  LoadBalancer services draw IPs from the
  cluster's LB range (Cilium LB IPAM) and are announced
  with L2 announcements, so a laptop on another subnet
  can reach a service IP through the normal gateway;
  BGP/EVPN advertisement to an external router (e.g.
  OPNsense with FRR) is the routed alternative.
* VXLAN zones also work; EVPN is the recommended fit
  for externally reachable LB IPs.

== Storage

* The Proxmox CSI driver is installed with the cluster.
  Two classes by default: *shared-block* (volumes on
  shared storage, attach anywhere) and *local-block*
  (node-local storage - faster, pinned to one fabric
  host). Disks hot-attach; no node shutdown is needed
  to change a volume's backing.
* Local volumes follow their pods: if a pod with a
  local PV is rescheduled to a node on another host,
  the scaler detects the stuck volume and moves the
  disk to that host (`POST /cluster/k8s/{name}/volumes/move`
  does the same manually). Shared volumes never move.
* Shared-file (RWX) classes are opt-in at create time:
  NFS (`file-backend nfs` with server/share) or CephFS,
  both via CSI, validated by a probe before the class
  is offered.

=== Storage profiles and failure policies

At creation you pick one storage profile: *shared*
(Ceph RBD node disks, shared pod volumes) or *local*
(node-local disks and volumes). Each node group may
override its disk storage (under its advanced fields).

What happens when a node or its host fails is a
per-group *failure policy* (control plane: `cp-policy`;
worker groups: `policy` in the group editor):

* *replace* (default) - the plugin rebuilds the node:
  workers with a fresh VM, control-plane members
  remove-then-add under a fresh name when the old member
  is confirmed dead (surge add-then-remove when it is
  still alive). If no eligible host exists, the pool
  *parks* - shown in the Overview - and resumes when one
  returns.
* *ha* - Proxmox HA reboots the VM on a peer host. Only
  selectable when that group's disk storage is shared
  (worker groups also need shared pod storage): on local
  disks HA would relocate the service without its disk.

In both modes, node VMs are registered with
pve-ha-manager and the datacenter shutdown policy is
set to `migrate`, so a planned host shutdown
live-migrates node VMs away first - local disks
included. HA mode leaves failure restarts to Proxmox;
Replace mode disables restarts (`max_restart=0`,
`max_relocate=0`) and the scaler waits a grace period
(15 min for HA groups, 5 min otherwise) before it
replaces anything itself.

== Add-ons

pve-k8s manages its add-ons from one catalog
(`PVE::K8s::Addons`): each has a tier, the version this
release pins (per Kubernetes minor where needed), and
where its running version is read in the cluster.

|===
| Add-on | Tier | Notes

| cilium (with gateway-api CRDs)
| core
| CNI, LoadBalancer IPs, ingress and Gateway; the
  Gateway API CRDs update with it

| proxmox-ccm
| core
| labels nodes with zone/region, sets providerIDs

| proxmox-csi
| core
| shared-block + local-block classes (above)

| shared-file
| storage
| NFS or CephFS driver, when the cluster has a file tier

| metrics-server
| default
| installed by provision, can be turned off; feeds the
  pod CPU/memory section of the Metrics panel
  (`--kubelet-insecure-tls` for the lab PKI)

| cert-manager
| optional
| enable with an issuer: the built-in CA (`ca`,
  default) or ACME (`acme`, with account email and
  directory URL)

| external-dns
| optional
| enable with the PowerDNS provider (`pdns`), API URL,
  key and zone; the key is kept only in the in-cluster
  Secret
|===

The Add-ons panel shows each add-on's status, the
version running in the cluster and the version pve-k8s
pins. When they differ, *Update* re-applies that add-on
at the pinned version with its stored settings, and
*Update All* does so for every add-on that is behind,
core add-ons first (a failing core add-on stops the
run). A Kubernetes upgrade does the same for the target
minor before it rolls any node, so an add-on the new
minor needs (Cilium 1.21 for 1.37) is in place first; the
upgrade check lists those updates.

[source,sh]
----
pvesh get /cluster/k8s/c1/addons
pvesh create /cluster/k8s/c1/addons/cilium/update
pvesh create /cluster/k8s/c1/addon-updates
pvesh create /cluster/k8s/c1/addons/cert-manager/enable \
    --issuer acme --email ops@example.com
pvesh create /cluster/k8s/c1/addons/external-dns/enable \
    --provider pdns --pdns-url http://dns.example:8081 \
    --pdns-api-key SECRET --zone example.com
pvesh create /cluster/k8s/c1/addons/metrics-server/disable
----

== Metrics and observability

* Node VM CPU/memory comes from Proxmox itself (RRD):
  always available, no in-cluster agent, and the plugin
  never writes Kubernetes metrics into the Proxmox RRD.
* Pod CPU/memory appears in the Metrics panel only when
  the metrics-server add-on is enabled. Without it,
  there is intentionally no pod-level metrics source
  (cadvisor history is a separate, later topic).
* The Events panel shows recent Kubernetes events;
  Workloads shows deployments, pods and services,
  read-only (day-2 workload management stays in
  Kubernetes tooling).
* Every long operation is a PVE task; the bottom task
  log describes them in words ("Kubernetes Cluster c1 -
  Start VMs", "- Scale", "- Destroy", ...).

== The scaler

One leader (elected via a pmxcfs stamp) runs a periodic
pass per cluster - systemd `pve-k8s-scaler.timer` where
enabled - or one pass on demand with the Scale button /
`POST /cluster/k8s/{name}/scale`. A pass, in order:

. *Repair*: a worker NotReady for more than 5 minutes
  whose VM does not answer the guest agent is replaced.
  A NotReady node whose VM is alive is reported and
  left alone - the plugin never destroys a live VM on a
  kubelet's say-so.
. *Local-volume rescue*: pending pods pinned by a local
  PV to a host with no schedulable node get their disk
  moved to a host that has one.
. *Scale out*: pending pods (older than 2 minutes) are
  simulated against every group whose labels, taints,
  affinity, topology and resource requests they match,
  including `kubernetes.io/arch`. If more nodes of a
  group would place more pods and the group is below
  `max` (and some PVE host has 4 GiB free), `size`
  grows and provision creates the nodes.
. *Scale in*: a worker is removed only if it uses
  under 30% CPU and memory, all its non-DaemonSet pods
  fit on the survivors in simulation (affinity, PDBs
  and topology included), the group stays above `min`,
  the node is over 30 minutes old, and no scale action
  ran within the cooldown (10 minutes; Settings,
  `scale-in-cooldown`, in minutes). Removal drains
  through the eviction API with a time box; a drain
  blocked by a PodDisruptionBudget uncordons the node
  and ends the pass - nodes are never force-drained
  past a PDB by the scaler.

The scaler stands down unless the cluster state is
`ready` (never during provision, roll or upgrade).
There is no VPA equivalent: right-sizing requests is
left to Kubernetes tooling; HPA works unchanged since
metrics-server is a normal add-on.

== Backups

* `POST /cluster/k8s/{name}/backup` takes an etcd
  snapshot from a healthy control-plane member;
  `GET /cluster/k8s/{name}/backups` lists snapshots;
  retention is configurable in Settings
  (`backup-retention`). A `pve-k8s-backup.timer`
  (daily) drives scheduled backups where enabled.
* `POST /cluster/k8s/{name}/restore` restores a snapshot
  with `etcdutl` per member - including onto a fresh
  control plane if the original members are gone.
  Restore probing is exit-status based today; making
  it fail-closed is a recorded follow-up.

== Node and host operations

On the Nodes panel (and under
`/cluster/k8s/{name}/nodes/{node}/...`):

* *Drain* - cordon and evict (PDB-safe) ahead of
  maintenance.
* *Replace* - drain, delete and recreate the node from
  the current template.
* *Force Retire* - for a node whose VM is dead: removes
  the stale node record without draining (confirmation
  required; refuses healthy nodes).
* *Evacuate Host* (`.../hosts/{host}/evacuate`) -
  replaces every node of the cluster living on one PVE
  host, for host maintenance.

Node identity is always verified against the live VM
(name + host) before any reset/destroy: VMIDs are
recycled by Proxmox, and the plugin will not touch a
VM that merely inherited a dead node's ID.

== User interface

* *Datacenter -> Kubernetes*: the cluster list only
  (Create, Destroy, Reload). Double-click a cluster to
  open it. Nothing else lives here any more.
* *Left resource panel*: every cluster appears as a
  `k8s/<name>` resource at datacenter level (next to
  the PVE hosts - a Kubernetes cluster is
  datacenter-wide, not per-node), with a cubes icon and
  its state.
* *Cluster page* (click a cluster on the left), with a
  stock second sidebar like a VM page:
  - *Overview* - state (with ready icon), version,
    template revision, sizes, subnets, node groups,
    certificate level; actions Provision / Roll / Scale
    / Upgrade / Start VMs / Stop VMs / Kubeconfig.
    Destroy hides under the *More* menu in the top bar.
  - *Nodes* - node groups (Create/Edit/Delete) over the
    node list; Drain / Replace / Force Retire /
    Evacuate Host per node.
  - *Workloads* - Deployments / Pods / Services,
    read-only.
  - *Metrics* - node VMs from Proxmox; pods from
    metrics-server when enabled.
  - *Add-ons* - states (installed / unconfigured /
    not installed) with Enable/Disable where supported.
  - *Events* - recent Kubernetes events.
  - *Backups* - snapshots with Backup / Restore.
  - *Settings* - maintenance window, backup retention,
    description; read-only details below.

[[multiarch]]
== Multi-arch (amd64 / arm64)

Proxmox VE ships an official ARM64 build and a Proxmox
cluster may mix architectures; a VM never changes arch,
so architecture is a property of a *node group*, not
of the cluster:

* group `arch` (`amd64`/`arm64`) is validated at save;
  placement only ever chooses PVE hosts of that arch,
  and templates are per arch
  (`k8s-node-<minor>-r<rev>-arm64`; amd64 keeps the
  historical unsuffixed name, built from the matching
  Debian cloud image, `--arch` on `build-template.sh`);
* kubelet already labels nodes `kubernetes.io/arch`, so
  pods pin architectures with ordinary nodeSelector /
  affinity - no plugin API needed on the pod side.
  Simulated scaler nodes carry the group's arch label,
  so an arm64-only pending pod scales an arm64 group,
  never an amd64 one;
* the control plane stays homogeneous: `cp-arch` at
  creation (the selector only matters on mixed-arch
  Proxmox clusters);
* kubeadm, helm and image downloads pick their arch from
  the guest at runtime - nothing is hardcoded to amd64.

Status: implemented and unit-tested; the amd64 path is
acceptance-tested end to end. ARM64 is *untested on
real hardware* (the validation lab is x86-only) and is
not claimed until an ARM Proxmox host exists.

== Packaging and integration

`make deb` builds `pve-k8s-manager_<version>_all.deb`;
`make test` runs lint plus the unit suite. The
maintainer scripts apply the eight integration points
of `INTEGRATION.md` to stock pve-manager files
(API registration, config registry, UI view and script,
resource entries, tree type, workspace routing, task
descriptions), idempotently, with `<file>.pve-k8s.bak`
backups; uninstalling reverses exactly those edits.
Cluster configuration under `/etc/pve/k8s` is user
data and kept. The plugin UI script URL carries a
content hash, so package upgrades are never masked by
a browser cache.

[[limitations]]
== Known limitations

* Physical-hardware validation (T4.2) has not run: no
  real host power-off or Ceph shared-block test yet.
  Nested-lab proof only; do not treat as
  production-ready.
* Hard control-plane anti-affinity (P2) and automated
  fencing/STONITH (P3) are open. Host-failure recovery
  is manual: do not power off a host whose CP nodes are
  needed for etcd quorum or hold the VIP alone.
* Kubernetes 1.37 is held until its add-ons are tested.
* ARM64 is untested until an ARM Proxmox host exists
  (above).
* A worker that dies mid-provision can leave the
  cluster record in `provisioning` until the next
  provision pass (state lease/resume is a recorded
  gap); rerunning Provision converges and adopts
  orphans.
* Restore probing is exit-status based, not yet
  fail-closed.
* For fresh nested labs, LVM-thin is recommended over
  ZFS (memory footprint); either works on hardware.

== Safety notes

* Control-plane VMs spread across hosts/HA groups on a
  best-effort basis; hard anti-affinity is not yet
  enforced (above).
* There is no automated fencing. Before powering off a
  host manually, evacuate it (Nodes -> Evacuate Host)
  or make sure its control-plane nodes are not needed
  for etcd quorum and do not hold the VIP alone.
